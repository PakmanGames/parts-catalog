## Read first

From `docs/PRD.md`:

- **Section 6 (Data):** what we already know and the checklist of what to learn.
- **Section 4, R1.3 and R1.5:** how parts are identified, how duplicates are resolved, and when to normalize or reject a row.
- **Section 7.1:** the draft `parts` table your profile will finalize.
- **Section 8:** confirmed facts C1 to C12 and assumptions A4 and A13.

The identity rules you need, in short:

- A part is identified by **supplier plus part number** (C2).
- Two values are "the same" after applying `normalize_key`: uppercase, then keep only `A-Z` and `0-9` (C10, C12, A13).
  In DuckDB: `regexp_replace(upper(x), '[^A-Z0-9]', '', 'g')`.
- When the file repeats a part, the row with the **newest last-updated timestamp** wins (C3).
- If the newest timestamp is shared, the **later line in the file** wins (A4).

## How much to read

- **Explore on the first 20,000 rows.**
  Use them to learn the header, the columns, and the formats each column uses.
- **Count on the whole file.**
  Every number in the profile comes from the full file.
  DuckDB scans it in seconds, and aggregate queries put no raw rows in your context.
  A sample alone would give wrong answers here: copies of the same part can be hundreds of thousands of lines apart, and rare problems may not appear in the first 20,000 rows at all.
- **Examples:** quote at most 5 per problem in the profile, verbatim, each with its line number.

Starting point:

```sql
-- Load every column as raw text, so nothing is silently converted.
-- store_rejects keeps lines DuckDB couldn't parse instead of failing.
CREATE TABLE raw AS
  SELECT * FROM read_csv('<path>/parts_export.csv', all_varchar = true, store_rejects = true);

CREATE VIEW sample AS SELECT * FROM raw LIMIT 20000;

SUMMARIZE raw;       -- per column: null %, distinct count, min and max
FROM reject_errors;  -- lines that couldn't be parsed, such as a wrong column count or bad quoting

-- A column's formats: letters become "a" and digits become "9".
SELECT regexp_replace(regexp_replace(<column>, '[A-Za-z]', 'a', 'g'), '[0-9]', '9', 'g') AS shape,
       count(*) AS n
FROM raw GROUP BY shape ORDER BY n DESC LIMIT 30;
```

DuckDB doesn't number the lines for you.
`row_number() OVER ()` over the scan follows file order, because DuckDB preserves insertion order by default, so a row's line is usually that number plus one for the header.
Lines that `store_rejects` dropped, and quoted fields containing line breaks, shift that numbering.
Confirm a few rows against the file with `sed -n '<line>p'`, and record how you numbered lines, since WS-A's error messages must point at real line numbers.

## What to find out

### 1. The file itself

- Exact header text, delimiter, quoting style, encoding (including any byte-order mark), and line endings.
- Total lines from `wc -l` versus rows DuckDB parsed.
  Explain any difference.
- Lines that can't be parsed (wrong column count, broken quotes, embedded newlines), with counts and line numbers.

### 2. Every column

For each column:

- What it means, and which PRD field it maps to: part number, supplier, quantity (stock on hand), price, lead time, last updated, or something else.
  Any column the PRD doesn't mention, such as a description or unit of measure, needs a recommendation: keep or drop, and why.
- Blank and null counts, including whitespace-only values and sentinels such as `N/A`, `-`, `TBD`, `0`, `-1`, or `9999`.
- Its value shapes, with counts.
- The target Postgres type and whether it can be null.

Column-specific questions:

- **Price:** currency symbols or codes, thousands separators, decimal commas, the largest number of decimal places (this sets the `numeric` scale in PRD 7.1), zero, negative, and absurd values, and ranges or "call for price" text.
  Which currency is it (PRD Q8)?
- **Quantity:** whole numbers only?
  Decimals, negatives, thousands separators, text such as "10+" or "in stock"?
- **Lead time:** what units (days, weeks, business days), what text formats ("2 wks", "ASAP", "stock"), and how often it's missing.
  Propose an exact rule for turning each format into whole days, or rejecting it.
- **Last updated:** every timestamp format, time zones or offsets, invalid dates, dates in the future or the distant past, and numeric epochs.
  Propose how to read each into a `timestamptz`, and what time zone to assume when none is given.
- **Part number:** which characters appear, leading or trailing spaces, and how many values become empty after `normalize_key`.
- **Supplier:** list **every distinct spelling**, grouped by `normalize_key`, with row counts.
  Check that no group merges two suppliers that are really different.

### 3. Identity and duplicates

Using `normalize_key` on both supplier and part number:

- Rows in the file versus distinct parts.
- Number of duplicate groups, and the largest group.
- How far apart copies of a part are in the file (line distance: median and maximum).
- Groups whose copies have different values.
- Groups whose **newest** timestamp is shared by two or more rows with different values (the A4 tie case).
- Groups where the newest row would be **rejected** by one of your rules.
  Don't decide what should happen there.
  List it as an open question for T0.3: does the next-newest valid row win, or is the part skipped?

### 4. Distributions for WS-B's benchmark data

- Number of suppliers, and rows per supplier: minimum, median, maximum, and the top 5.
- Part number length (minimum, median, maximum) and the 10 most common shapes.
- Percentiles (p1, p50, p99, max) for quantity, price, and lead time in days, after your cleaning rules.
- Share of rows with zero stock and with missing lead time.

## Rules for each problem

Give every problem an ID (`P1`, `P2`, and so on) and a rule that WS-A can implement and test without asking anyone:

- **Normalize** when the intended value is unambiguous, for example `" 1,200 "` becomes `1200`.
  Say exactly how.
- **Reject** when it isn't, with the exact rejection reason text the import summary will show (PRD R1.6), for example `price is not a number`.
- **Needs decision** when you're genuinely unsure.
  Explain the options and leave it for T0.3 instead of guessing.

Prefer rejecting over guessing (PRD NFR3: correctness over coverage).

## Output: `docs/data-profile.md`

Use this structure:

1. **Summary:** a short paragraph and a table of key numbers (rows, distinct parts, duplicate groups, rows that would be rejected, suppliers).
2. **File format:** header, delimiter, quoting, encoding, line endings, and parse failures.
3. **Columns:** a table of CSV column, PRD field, Postgres type, nullable, and notes.
4. **Data problems:** a table of ID, column, problem, count, examples with line numbers, and rule.
5. **Identity and duplicates:** the findings from "What to find out", part 3.
6. **Distributions:** the numbers from part 4.
7. **Answers to PRD questions:** Q8 (currency and units), and whether the A4 tie case actually occurs.
8. **Open questions for T0.3:** everything marked "Needs decision".
9. **Reproducing this profile:** the DuckDB queries behind every number, so T0.3 and WS-A can re-run them.

Write it for a reader who hasn't seen the data.
Put each sentence on its own line, and use a plain hyphen, never an em dash.
